# Mid/long-term evaluation — 17 September 2026

**Isolated approach evaluation; not a deployed planning replacement.** The final direction and remaining integration requirements are in `mid-long-term-approach.md`. This chronological record follows `scope-diagnosis-0.14.22.md` and `single-pass-evaluation-2026-09-16.md`; interim statuses below describe their respective experiments. ## What has to work

An episode must be able to finish without owning the entire future. Preparation must contain substantive, compatible invention, not only another hook, the same problem's fallout, or hobbies substituted for the RP's genre. The middle must actually unfold through play, survive refusal and distraction, and reach changed circumstances. Private proposals must not become invented accepted history. The user must not have to author all the interesting progress for the planner.

### User clarification: seamless play is required

The user clarified during this evaluation that “I'm done with this arc” was feedback to the coding assistant, **not an OOC directive they intend to issue during RP**. They almost never declare an arc finished and generally play seamlessly. Therefore earlier forced-closure/time-jump probes are stress tests of preservation/conditional uptake only; they do not pass the natural-transition acceptance target. The complaint must remain an evaluation requirement, not be silently installed as an in-world planner instruction. The historical-instruction binding prototype is not a remedy for this distinction and is not approved for integration.

The next acceptance run must use ordinary in-character actions/dialogue, let NPCs and situations develop from accepted causes, and demonstrate natural episode closure plus wider progress without a test message declaring the job over or demanding “mid-to-long-term” content. A local episode also needs a finite resolution basis, so defeating one obstacle does not automatically author another hidden layer of the same problem. The user's live September 17 snapshot remains mid-assault at the weigh-house; it has not been declared finished or edited for the experiment.

## A further diagnosis: caution can prevent authorship

The first concrete staging attempt repeatedly conflates two rules:

1. Memory must not claim an NPC agreed or acted unless an accepted message establishes it.
2. A storyteller **may author a new NPC agreement/action in the upcoming reply** without waiting for a prior message to contain it.

It stages another offer to play after the user already asked to try the music, then puts “do not assume Jo agreed” in the boundary field. The writer reproduces the offer. This is not simply a lack of tokens or absent preparation: the desired subject is present, but the handoff discourages enacting it. A revised staging task explicitly separates accepted memory from new NPC authorship while retaining player agency and source constraints.

## Prototype ownership boundaries

- Complete source scope is separate from generated framing; context overflow fails explicitly rather than clipping it.
- Broad preparation owns a bounded repertoire of concrete future material. Routine calls cannot replace it with the latest scene recap.
- Routine memory appends accepted changes with supplied indices and retires resolved local records. Index validity is not semantic proof of a claim.
- Staging is disposable, explicitly unaccepted authoring material. It is never automatically copied into accepted history. Invalid staging is rejected without destroying durable preparation or reusing stale scene directions.
- Broad review transactions must explicitly retain/replace/retire every previous development. Replacements archive the previous version and its branch invalidations. Accepted observations survive separately. A review based on stale accepted progress is rejected. These review transactions have unit coverage, not yet a live generated-review acceptance test.

The prototypes intentionally use complete bounded inputs (up to 24,000 estimated tokens), not the installed routine budget. Production integration would still need an explicit budget and retrieval policy that does not hide the middle of a record while allowing its replacement.

## Writer-preset interaction: newly inspected, not yet established as the cause

Read-only inspection of ST source verifies that OpenAI-family prompt ordering uses global dummy ID `100001`. Enabled flags come from that order, not the misleading per-prompt `enabled` field. The user's active writer source is native DeepSeek, model `deepseek-v4-pro`, Low reasoning, 60,000 context and 6,000 output. Earlier tests used the planner's custom route and synthetic writer instructions, so their failures cannot be attributed to this preset.

The enabled preset says to keep one CURRENT beat, keep HELD threads inactive, avoid unrelated events, stop broad actions after the first meaningful phase, and never advance merely to reach a later event. Its pre-prose stat says time-only input changes only Time & Weather, leaving other player fields unchanged. These are sensible agency/pacing protections, but their interaction with an explicit time-and-place transition and a request to experience prepared future material needs testing. Changing them wholesale or silently would not be justified.

The isolated preset-informed adapter preserves the enabled static prompt text and reproduces the verified depth-one role grouping/order. It does not reproduce runtime World Info, Continuity retrieval, all macros or native provider transforms. The comparison uses the matching writer model/temperature/Low reasoning through the separate custom route. A labeled compatibility variant distinguishes scene scope from campaign scope and a requested experience from an invitation, while preserving player decisions. Nothing is written to ST.

No basis yet to recommend changing the user's preset. Existing instructions, source reconstruction, sampling/reasoning and planner material must not be conflated as one cause.
