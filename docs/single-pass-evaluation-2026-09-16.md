# Single-pass mid/long-term evaluation

Status: **candidate not accepted as a fix**. Evaluation-only prototype; not imported by the extension, installed, or committed. The bounded live run stopped on an upstream HTTP 502, with 13 successful completions from 14 requests. Results below distinguish observed failures from untested checks.

## Question

Can one planner response prepare sustained developments beyond the current episode AND select useful present material, without the latter responsibility swallowing the former?

Broader labels, more records and an occasional new quest are not acceptance. The primary criterion is viable mid/long-term progression. Immediate writer material is checked for compatibility and regressions, not used as a substitute for that criterion. Creative range is judged from concrete possibilities and their workings, not sampling randomness or the planner's own independence labels.

## Candidate boundary

- `scripts/single-pass-planner-prototype.mjs` supplies a separate evaluation system contract, complete source-reference reservation and routine approach-write protection. It reuses the existing schema and omission-preserving merge. Production modules are unchanged.
- One completion per stage/arm. No critic, repair, retry or AI grading call.
- A broad run prepares continuing developments and current writer material in the same response. A routine run maintains/reconciles them and selects current material in the same response.
- The current storage already preserves omitted records; the experiment does not claim to have invented that feature. Routine scope protection alone is not a semantic guarantee that every updated record remains good.
- Oversized complete references fail closed. Scalable extraction for very large cards and triggering a broad review when explicit scope changes are production integration work, not solved by this prototype.

## Predeclared comparisons

18 calls maximum, using the existing configured planner model and sampling, with reasoning requested off. Requests go directly to its configured provider/proxy; the running SillyTavern server is not used. Credentials remain in memory, never in artifacts. Inputs and generated states are written only outside the repository. The live user chat is not reread or advanced during testing.

1. **Frozen actual context:** paired broad reviews of the previously captured saved notebook and context. Both arms receive the same explicit user preference not to extend this particular arc. The candidate does not receive a cleaned notebook or handpicked future plans. The JSON payload is identical between arms; system/schema differ.
2. **Synthetic touring company:** paired seven-stage sequences, each with its own persistent notebook. Both begin with the same locally captured costume-delivery investigation. Accepted continuations are fixed before generation: local pressure; explicit episode closure; user-chosen travel; development of an NPC musical collaboration with a refusal of public performance; an unrelated dinner problem; a later review. The planner must prepare beyond delivery, preserve it under local attention, reconcile actual intermediate changes and avoid treating a private experiment as an accepted public booking.
3. **Deliberately closed evening:** paired broad reviews must deepen an ongoing family interaction without inventing a journey, campaign, sequel or external crisis.

The synthetic sequence explicitly supplies accepted transitions and the musical changes. Therefore it tests the planner's preparation, adaptation and writer packet, NOT whether an autonomous writer naturally creates those transitions. Distinguish invented preparation from developments handed to the model by the fixture. There are five routine calls between two reviews, not a full twelve-call review interval. A separate twelve-merge unit test checks storage only, not AI behavior over twelve runs.

## Semantic inspection rubric

- Does new preparation have concrete, causally independent substance beyond the episode? Does it offer more than another problem with renamed people?
- Does an enduring development contain meaningful intermediate experiences, possible changes and later relevance, without a fixed itinerary or predetermined player behavior?
- Do subsequent outputs preserve useful details and revise accepted changes rather than reset the hook, multiply copies or absorb everything into the newest problem?
- Can the local episode actually close? Does unresolved preparation avoid turning into a compulsory sequel?
- Does the current writer packet remain usable and appropriately scoped? Are later proposals kept private until relevant?
- Are identity, agency, accepted commitments, refusals and knowledge boundaries preserved?
- Does the deliberately closed case stay closed?

All pass/fail judgments must cite output content. Successful JSON validation or retention of an ID is not a creative success.

### Why storage retention is not enough

The actual inputs expose another constraint the candidate did not solve. At the accepted-development stage, baseline full records are only `carrier_questions` and `mere_travel_plan`; candidate full records are only `theatre_deadline` and `jos_composition_ambition`. Other records have been reduced to ID/status/premise lookup tuples to fit the routine envelope. The candidate has the relevant Jo middle here, but stale local records still consume a protected full-record slot. A rotating wider slot is not automatically useful long-term attention.

The broad scope is protected, but the prototype still uses the same flat replacement-record contract, current-selection machinery and shared budget. An AI can rewrite a record whose previous middle it cannot see; omission-preserving storage alone does not protect that middle during a replacement. Some responses therefore reconstruct from recent events and the summary rather than deliberately carrying forward the actual prepared alternatives. This is a concrete architectural limitation, not proof that extra instructions or tokens can never help.

The report's raw `omittedIdsRetained` flag is false on both synthetic initial reviews because their seed records acquire normalized empty optional fields; it is not evidence that those records were lost. A post-run audit compared all 44 omitted-record instances after normalizing both sides: zero retention differences. Engineering retention tests also compare normalized records. The source-reservation stress test and routine-write guard are primarily offline checks: both real-review payloads already contain the same source, the synthetic source is short, and the completed candidate routine responses omit approach without needing the host to remove it.

## Decision and next bounded approach

**Do not deploy this candidate as the mid/long-term fix.** It demonstrates some one-pass continuity and selection, but not sufficient invention or reliable independence on the user's actual context. Neither schema validity nor keeping more IDs warrants accepting it. The failed request also leaves the planned late/closed checks incomplete.

The next experiment should change the representation and input allocation, not merely add another reminder to think broadly:

1. Keep authoritative RP scope/preferences separate from generated framing. Preserve explicit scope changes; a routine lock must not freeze obsolete user intent.
2. Give enduring developments a distinct section and protected input space, separate from the current episode and writer selection. Carry a concise accepted-state/change record alongside concrete conditional preparation, so a long-running pursuit can change without its entire middle becoming the latest scene recap. Do not implement near/mid/far bins containing three versions of one problem.
3. On broad preparation, ask for distinctive actors, practices or processes and meaningful intermediate possibilities that are not already supplied by the latest scene. Keep inventions explicitly provisional. Do not use fixed plot routes, mandatory novelty quotas, or a host heuristic that claims to judge creativity from labels.
4. Reconcile episode closure and duplicate ownership across the notebook; merely hiding old records leaves misleading premises competing for future attention. Preserve genuine unaccepted alternatives and accepted commitments rather than deleting everything local.
5. Keep preparation and current writer selection in **one completion initially**, but express them as distinct output responsibilities. Test novel preparation before handing it a successful continuation, then test accepted development, refusal, distraction, closure and a later review. Include a writer-mediated continuation before claiming end-to-end viability.

This is a justified next hypothesis, not an approved production route or a promise that one pass must succeed. The current experiment changed the system contract, source fitting and scope ownership, but did not implement separate durable-development storage. If that next controlled comparison also fails creative preparation, compare a dedicated preparation call rather than endlessly polishing the same prompt.
